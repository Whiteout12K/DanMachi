## Launch and containment

Run `Launch DanMachi.command` in the project root; it prints launch failures. `DanMachi Mac.app` is an optional shortcut and writes to `state/logs/launcher.log`, but generated Android/ANGLE cache files inside its bundle can invalidate its code-signature resource inventory. On this copy, strict signature verification reports those generated cache files; use the root command launcher if macOS refuses to open the app. launcher/game.py runs the folder-local signed compatibility executable directly, rather than using Mac.apk's generated stub or the globally shared runtime. The generated stub's outside-runtime symlink was removed. Mac.apk recreates its Music, Pictures, Download, Movies and Documents links on launch. The wrapper replaces only those symlinks with folder-local empty directories before launching and after exit, without touching their destinations. The sandbox denies access to the host shared media folders/Downloads except this project, denies reading the Drive tree and global Mac.apk state, and denies writes elsewhere under the user home directory. OS services and crash reports remain host facilities; this is not a claim that macOS itself stores nothing outside the project.

When the project is launched from `Library/CloudStorage`, the sandbox permits metadata checks on its ancestor directories so the runtime can resolve its executable path; file contents outside the project remain denied.

## Meaning of no Android virtualization

There is no Android emulator, guest Linux kernel, system image, virtual disk, AVD, ADB or scrcpy here. Mac.apk still implements Android APIs, uses a JVM and provides Android compatibility resources plus a small emulated filesystem layout under DanMachi Mac.app/Contents/android. Those are required for the APK; it is impossible to keep an Android APK working while literally removing all Android compatibility components. The copied runtime's third-party notices remain under runtime/Mac.apk.app/Contents/Resources/.
